# Deployment Guide

Production topology: **Backend → Render** · **Database → Neon PostgreSQL** ·
**Frontend → Vercel**.

## 1. Database — Neon PostgreSQL

1. Create a project at https://neon.tech.
2. Copy the pooled connection string (used for the app) — looks like:
   `postgresql://user:password@ep-xxxx-pooler.region.aws.neon.tech/healthguardian?sslmode=require`
3. Convert it to the SQLAlchemy driver form the app expects:
   `postgresql+psycopg2://user:password@ep-xxxx-pooler.region.aws.neon.tech/healthguardian?sslmode=require`
4. Save this as `DATABASE_URL` — you'll set it on Render in step 2.

## 2. Backend — Render

This repo includes a `render.yaml` (Render "Blueprint") at the project root
that defines the web service.

1. Push the repo to GitHub.
2. In Render, choose **New → Blueprint**, point it at the repo — it will read
   `render.yaml` and create the `healthguardian-backend` service with:
   - Build: `pip install -r requirements.txt`
   - Start: `alembic upgrade head && gunicorn -c gunicorn.conf.py app.main:app`
   - Health check: `/health`
3. Fill in the environment variables Render leaves blank (`sync: false` in
   `render.yaml`):
   - `DATABASE_URL` — the Neon connection string from step 1
   - `BACKEND_CORS_ORIGINS` — your Vercel frontend URL, e.g. `https://healthguardian.vercel.app`
   - `REDIS_URL` — optional; a Redis Cloud/Upstash URL, or omit (rate limiting fails open)
   - `OPENAI_API_KEY` — optional; omit to run the chatbot/report-summary in offline fallback mode
   - `CLOUDINARY_*` — optional; omit to use local disk storage (note: Render's
     filesystem is ephemeral on the free/starter tier, so Cloudinary or S3 is
     recommended for persistent file storage in real production use)
   - `SECRET_KEY` is auto-generated by Render (`generateValue: true`)
4. Deploy. Render runs `alembic upgrade head` on every deploy, so schema
   changes ship automatically with each push.
5. Confirm health: `curl https://<your-service>.onrender.com/health`

### Manual (non-Blueprint) setup, if preferred

- Root directory: `backend`
- Build command: `pip install -r requirements.txt`
- Start command: `alembic upgrade head && gunicorn -c gunicorn.conf.py app.main:app`
- Health check path: `/health`
- Set the same environment variables as above.

## 3. Frontend — Vercel

1. In Vercel, **Add New → Project**, import the repo, set **Root Directory**
   to `frontend`.
2. Framework preset: Vite (auto-detected via `vercel.json`).
3. Environment variable: `VITE_API_BASE_URL` = `https://<your-render-service>.onrender.com/api/v1`
4. Deploy. `vercel.json` includes an SPA rewrite so client-side routing
   (React Router) works on refresh/direct links.
5. Once deployed, copy the Vercel URL back into Render's
   `BACKEND_CORS_ORIGINS` and redeploy the backend so CORS allows it.

## 4. Post-deploy checklist

- [ ] `GET /health` on the Render URL returns `{"status": "healthy"}`
- [ ] `GET /docs` loads the Swagger UI
- [ ] Register + login works end-to-end from the deployed frontend
- [ ] CORS: frontend can call the backend without console errors
- [ ] `BACKEND_CORS_ORIGINS` and `VITE_API_BASE_URL` point at each other's real URLs (not localhost)
- [ ] `SECRET_KEY` is a real generated secret, not the `.env.example` placeholder
- [ ] File uploads: confirm Cloudinary is configured, or accept that local
      uploads won't survive a Render redeploy/restart

## 5. CI/CD

`.github/workflows/ci.yml` runs on every push/PR to `main`/`develop`:
lint (ruff) → backend tests (pytest, SQLite) → backend Docker build → frontend
lint + build. Render/Vercel each auto-deploy from `main` on their own git
integration — this repo's CI is a pre-merge gate, not the deploy trigger
itself. Wire up branch protection requiring the CI workflow to pass before
merge for a real production-readiness gate.
